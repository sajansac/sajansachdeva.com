AI Makes It Cheaper to Build the Wrong Thing

Shipping got almost free. Shipping the wrong feature didn't.

I shipped my first product to a paying client last month — dashboard, forecasting engine, daily reports, AI chat — built almost entirely on Claude Code. My co-founder and I had drawn a line for what the MVP would be, what we’d demo. But with Claude Code, that line kept moving. We could do more, so we did. We ended up delivering something that went well beyond what the original prototype had in mind. The client loved it. Features that would have taken weeks shipped in hours.

And then the temptation kicked in. Because shipping was so fast, every idea started to feel worth trying. There were technically interesting problems we could have picked up, features that would have been genuinely fun to build. We probably could have shipped them fast too. But they would have pulled the product in a direction the client didn’t actually need it to go. So we discarded them.

Why this matters

That’s the thing that keeps sitting with me. AI didn’t just make it easier to build the right things — it made it equally easy to build the wrong things. The cost of shipping dropped to almost nothing, but the cost of shipping the wrong feature didn’t drop at all. If anything it went up.

Because the speed means you can quietly drift into becoming a different product, a different company, without even noticing. Three features that felt like quick wins and suddenly you’re solving a problem nobody asked you to solve.

Before AI-assisted development, I couldn’t build everything even if I wanted to. Scarcity did the prioritisation for me — I had to pick the right features because I could only afford to build a few. Now that natural constraint is gone entirely. And that changes what the job of building a product actually is.

What I’m doing differently now

The discipline to not build has to come from somewhere else now — not from engineering constraints, but from how well I understand the problem I’m solving. From continuously going back to my client and validating what they actually need rather than what I can build. From being willing to say no to something that’s easy to say yes to.

I’ve started asking a different question before picking up any new feature. Not “can we build this?” — the answer is almost always yes now. Instead: “if I remove this, would the client notice?” If the answer is no, it doesn’t belong in the product. No matter how fast it is to ship.

A good product isn’t one that does more. It’s one that’s more robust without being more wide. Simpler for the client to engage with, not impressive for how many things it can do.

I’m having a lot of fun building this. But the fun isn’t in the speed. It’s in getting sharper about what’s actually worth building.

The job of a founder in 2026 isn’t shipping. It’s knowing what’s worth shipping.
